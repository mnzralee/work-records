**VPS Disk Pressure Triage and the Layered-Cause Discovery:** The session opened with what was framed as a routine three-pass cleanup of the development VPS, but escalated within the first hour into a multi-hour incident response. The host showed eighty percent disk utilisation climbing to eighty-three percent under active write pressure, with containerd holding sixty-four gigabytes across eighty-six images, Docker holding one hundred twenty-two gigabytes across twenty-seven images including fifty-seven gigabytes of build cache, and the local-path persistent volume claim for the object storage service sitting at eighty-eight percent on the same backing partition. The seventy-one running pods were healthy on the surface except for two orphan debug pods and a critical storage service pod in CrashLoopBackOff with two thousand eight hundred seven restarts over thirteen days, restarting every forty seconds and adding churn faster than constrained pruning could reclaim. The conventional cleanup levers were essentially empty: dangling images returned zero bytes, build cache pruning with a one-hundred-sixty-eight-hour retention window returned zero bytes because all cached layers were within the active development window, and journald vacuuming returned zero bytes because all five hundred megabytes were within retention policy.

**Application-Layer Misdirection and the Object Storage Recovery Path:** With the user authorising a focus on the crashlooping storage service, the investigation dove directly into application internals. The service logs revealed ECONNREFUSED to the object storage backend, and the storage backend itself was reporting one-of-one ready according to the kubelet but dead from inside its own loopback because the StatefulSet carried no liveness or readiness probes and had been dead-but-ready for approximately two days. Hours were spent examining backend state files, format metadata, thread parking states which were misread as deadlocks when they represented normal Go runtime idle behaviour, signal-based diagnostics which failed because the distroless image lacked the kill binary, and version-pin investigations that surfaced a real on-disk format upgrade from version two to version three caused by a floating latest tag. The pinned release was rolled back to a verified compatible version, the corrupted backend was wiped, and fourteen megabytes of bucket data was restored from a host-side tar backup. The StatefulSet manifest was authored fresh with explicit liveness and readiness probes pointing at the canonical health endpoints, image pull policy set to if-not-present, and the dangerous stale deployment manifest targeting a phantom namespace was removed in the same change.

**The OSI-Bottom-Up Correction and the Ninety-Second Reframe:** After the storage backend recovered cleanly, the dependent service still failed with the same ECONNREFUSED signature, and a deeper investigation into linkerd proxy injection and identity-headless reachability led to the conclusion that the cluster carried a broader networking pathology beyond reasonable session scope. The user delivered a direct methodology correction at that moment, drawing the analogy that troubleshooting an electrical device begins at the outlet and the fuse, not by ripping apart the device, and that for networks the seven-layer model dictates starting at physical, data-link, network, and transport before application. The correction was captured immediately as a durable feedback memory with a five-step prescription beginning with the network-namespace TCP test from inside the affected pod and explicitly forbidding goroutine stack dumps, backend file inspection, or signal-based interruption before the basic reachability probe runs. Applying the corrected methodology, the pod sandbox process identifiers for the broken and a healthy peer pod were captured, layer-three ping succeeded from both namespaces with zero percent loss, but layer-four TCP connect to port nine thousand failed identically with connection refused from both pods, immediately overturning every prior pod-specific conclusion of the day. The real root cause was a NetworkPolicy egress rule that had been authored two weeks earlier by the parallel developer to allow port nine thousand to the data namespace, but had never been applied to the cluster; the kubectl diff confirmed exactly the single missing port, the apply landed cleanly, the pod came one-of-one ready in zero seconds on its first readiness probe, and the storage service was healthy for the first time in thirteen days.

**Phantom-Namespace Manifest Sweep and Cluster-Wide Drift Audit:** With the immediate incident closed, a comprehensive drift audit ran kubectl diff across every devnet manifest file against the live cluster state and classified each drift by direction. The audit also surfaced four service deployment manifests where both the repo and the live cluster were wrong in different ways: the live pods were pinned to specific image tags that no longer existed in the registry, while the repo manifests floated against latest tags, meaning any node change would trigger ImagePullBackOff cascades while the repo direction itself was the anti-pattern. Three multi-document manifests were undiscoverable by kubectl diff because the Prometheus Operator CRD for ServiceMonitor was not installed in the cluster, shorting the diff before evaluating the other resource kinds. The biggest lesson from the audit was that drift direction matters, the first instinct of applying repo to fix drift everywhere would have caused four pull failures and broken two probe paths because the repo was the stale side in those cases.
