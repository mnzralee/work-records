Backend Pipeline Wiring and Audience-Aware Email Templating
Tracing the full submission pipeline from form payload through the contact API, confirmation token, confirm endpoint, and Sheets append identified six gaps each addressed by a focused commit. The contact route was updated to validate the audience field against the canonical audiences tuple, enforce server-side consent presence by returning a 400 status when version or acceptedAt were absent on a pre-registration submission, and inject both audience and consent metadata into the confirmation token payload. A copy correction across three locations clarified that pre-registration is an interest form for the early-access mailing list and does not guarantee on-chain registration, allocation, or any unit grant.

Five-Bug Submission Chain and the Type-Checker-Versus-Integration Discipline
With forms rendering and the backend wired, actual submission still failed and three layered bugs surfaced in sequence each visible only after the prior was repaired. The first was a 403 forbidden-origin response because the development server ran on port 4545 while the origins allowlist covered only the 3000 range, resolved by adding both localhost and 127.0.0.1 host forms. The second was a 503 rate-limiter-unavailable response because the Redis-backed limiter had no graceful fallback for local development; the helper was renamed from isTestEnv to useInMemoryFallback and rewritten to return true when the runtime was not production and REDIS_URL was unset, preserving the fail-closed production posture. The third was a 400 captcha-failed response concealing two stacked bugs: the page component destructured a fixed list of props and missed enableCaptcha, causing the form engine to default it to true and render the math captcha despite the registry setting it false for pre-registration; the fix replaced the brittle destructuring with a spread. The deeper server-side layer enforced the captcha unconditionally whenever CAPTCHA_SECRET was set, resolved by wrapping the enforcement block in a pre-registration guard since pre-registration verifies humans through email confirmation rather than a math challenge. The discipline insight codified from the chain was that tsc --noEmit returned exit zero throughout all five failures, confirming that integration-level pipeline failures require a real HTTP POST against a running server rather than a type-level check.

Missing Form Engine Renderers and Playwright End-to-End Verification
Two field types declared in the audience manifests had no renderer in the form engine and would have degraded to broken text inputs in production. Two parallel agents implemented the missing renderers: a segmented control for the Government form's procurement interest field using a role-radiogroup container with pill-style buttons, roving tabindex semantics, and arrow-key navigation; and an autocomplete renderer for the Business form's industry selector, filtering against a configurable options list, closing on exact match, and using onMouseDown with preventDefault to prevent blur-before-click from swallowing the selection. A follow-up fix closed the country dropdown on exact-match selection, which had remained open during the verification pass. A Playwright headless Chrome run exercised all four forms against the development server on port 4545, filling all fields including country autocomplete selection and the Government segmented control, clicking consent, submitting, and asserting the check-your-email success screen with zero console errors and zero 4xx or 5xx responses. All four forms passed — the Individual form at /pre-registration, the Business at /for-businesses/pre-registration, the Non-Profit at /for-non-profits/pre-registration, and the Government at /for-governments/pre-registration — each returning a 200 response with a Resend confirmation identifier, with specific assertions covering the full metadata map, audience tag, consent version, and consent acceptedAt in the submission payload.
