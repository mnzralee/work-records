Title: Service Extraction Sprint: Carving the Partner Service Out of the Organization Service Through an 11-Track Clean Architecture Migration

Objective:
To execute a full microservice extraction by carving the partner domain out of the organization service into a standalone Clean Architecture service, governed by an adversarial review-board process, while simultaneously closing two pre-existing CI failures and embedding five priority-zero security amendments directly into the new service's bootstrap layer. The work was scoped to deliver the new service at production-grade quality on its first compile, with zero non-test compilation errors, faithful preservation of the existing test suite, and complete integration into the monorepo's Turborepo and Kubernetes deployment surfaces. A secondary goal was to convert what would otherwise have been silent architectural drift, hidden security gaps, and a port-allocation collision into loud, documented findings before any code moved.

Work Carried Out:

**The Architectural Question That Reframed the Day:** The session opened expecting routine carry-forward work: closing two known CI failures from the previous day, deploying remaining services, and finalising the production-readiness scorecard. The trajectory shifted when the question was raised whether the partner module, which had grown inside the organization service, deserved its own service boundary given its scope around API key licensing, validator operations, and a 45-endpoint external surface. Reading the partner ecosystem specifications revealed seven partner categories spanning financial service providers, payment management, insurance, marketplace, credit, validation, and tip operators, each anchored to a multi-phase lifecycle pipeline running three to eight months, with independent revenue, lending, and settlement domains. What had been treated as a feature of the organization domain was, in fact, an entire ecosystem with its own bounded contexts, security model, external API surface, and rate of change, and that recognition justified pausing the planned work to make the extraction the day's primary deliverable.

**Evidence Gathering Through Four Parallel Research Agents:** Before any code moved, four research agents were dispatched in parallel to build the evidence base for the extraction decision. The first agent surveyed the partner ecosystem specifications and identified at least three distinct bounded contexts, with arguably five or six if lending, validators, and settlement were separated. The second agent quantified the host service's bloat at 387 TypeScript files and 41,444 lines of code, with partner-specific files outnumbering organization-specific files by a 2.4:1 ratio, and the partner use-case tree alone exceeding the file count of multiple standalone services in the monorepo. The third agent mapped everything that should remain in the organization service: proposals, endorsements, multi-signature flows, stakeholders, merchants, budgets, compliance, and reporting, all of which formed a clean and stable bounded context. The fourth agent confirmed that all 25-plus partner Prisma models were partner-exclusive, with only two shared entities, meaning the two services could continue using the same shared database client under a tactical Strangler Fig pattern without requiring a schema split. The convergent evidence, combined with size, divergent rates of change, distinct security postures, and external-versus-internal exposure, made the extraction decision unambiguous.

**Adversarial Validation Through a Six-Agent, Three-Wave Review Board:** With the eleven-track extraction plan drafted across tracks A through K covering scaffold, domain, application, infrastructure, interface, dependency injection, host-service cleanup, tests, CI integration, CI fixes, and post-extraction verification, an adversarial Super Engineer Review Board was convened before any track was approved. Wave one ran three parallel agents covering architecture, industry standards, and security. The architecture agent identified that the planned parallel track execution was structurally wrong because TypeScript imports impose a sequential dependency chain forcing domain to precede application, then infrastructure and interface in parallel, then dependency injection, then cleanup. The industry standards agent caught that the originally proposed port 3055 was already allocated to a sibling service in the API gateway configuration, a silent collision that would only have been discovered at deployment time. The security agent surfaced two critical findings: the shared error handler in the core errors package leaked internal database table and column names through generic 500 responses, and the constant-time HMAC mitigation lived in a separate webhook dispatcher worker rather than the host service, meaning it would not move with the extraction. Wave two ran two parallel agents covering production readiness and code quality, the latter delivering a clean nine-of-nine pass with zero `any` types, zero suppressed compiler directives, zero silent catch blocks, and zero untyped errors. Wave three synthesised the findings into a "go with amendments" verdict carrying five priority-zero must-fix items, seven priority-one fix-during-extraction items, and five priority-two tech-debt items.

**Track A Scaffold With Five P0 Amendments Embedded At Bootstrap:** The orchestrator hand-wrote the five skeleton files following the cleanest reference Clean Architecture service in the monorepo as a template. The configuration file used port 3056 rather than the originally planned 3055 to resolve the review-board's port-allocation collision. The application entry placed OpenTelemetry initialisation as the very first executable line before any Express or logger import, matching the pattern established by sibling services. The application bootstrap incorporated all five priority-zero amendments directly: an explicit CORS origin allowlist replacing the wildcard default that had previously left the development network internet-accessible, a sanitising error wrapper that intercepted non-domain-typed exceptions and replaced raw error messages with a generic "Internal server error" response in non-development environments, a faithful Helmet content security policy replication, a trust-proxy setting calibrated for the Kubernetes ingress, and the dependency on the shared events package needed by partner use-cases that emit outbox commands. The discipline of folding security amendments into the bootstrap rather than appending them later eliminated the class of regressions where a remediation gets approved but never lands.

**Tracks B Through E: The Layered File Migration:** The domain layer landed first with seven files: two validator entities, the decimal value object, the fabric identifier derivation service, partner and validator error classes, and a barrel export, with an import-violation check confirming zero infrastructure or application dependencies as Clean Architecture demands. The application layer was the heaviest phase at 78 files, dispatched across three parallel sub-agents partitioned by bounded context: the first handled lifecycle, early-adopter, all shared ports, data transfer objects, and the admin snapshot service; the second handled settlement, staking, and service-level agreements; the third handled validator, query, API, team, and webhook sub-domains. Each sub-agent applied the priority-one amendment that replaced 15 hardcoded outbox source-service strings from the host-service value to the new service value, with post-merge verification confirming zero remaining stale references across the entire application layer. The infrastructure layer landed 19 files spanning partner repositories, validator repositories, webhook delivery logs, the outbox repository, the on-chain balance query service, the webhook dispatch service, two schedulers for validator rewards and webhook retries, and the atomic outbox transaction implementation. The interface layer landed 13 files covering five controllers, two route files, and five authentication middleware files, with the auth middleware adapted to import the new service's configuration rather than the host service's.

**Tracks F, G, H: Wiring, Surgical Disconnect, and the Verification Gate:** Track F consolidated three previously separate dependency injection modules from the host service into a single 290-line unified container following the reference Clean Architecture pattern, addressing two priority-one amendments by instantiating both the standard outbox repository and the atomic outbox repository independently and documenting the F-series security mitigation residency directly in the file header. Track G applied a surgical disconnect rather than a destructive removal, unwiring the partner routes, dependency injection imports, and scheduler lifecycle from the host service while retaining the original source files as dead code for rollback safety, on the principle that file deletion belongs in a future cleanup phase after the new service is verified live in the cluster. Track H ran the critical verification gate: the first invocation of the TypeScript no-emit compiler on the new service reported 70 errors. Triage revealed 24 fixable extraction gaps, including an outbox repository port missed because the copy glob matched only files containing "partner" or "validator" in the name, a stakeholder repository port needed by the organization-membership middleware, a webhook delivery error class buried in the host service's monolithic errors file, an incorrect import of a non-existent shared error symbol, and two enum casts requiring explicit type assertions. The remaining 46 errors were pre-existing test mock-shape mismatches identical to those in the host service's test suite, confirming they were not extraction regressions. After the 24 gaps were closed, a re-run reported zero non-test compilation errors, certifying the extraction as structurally sound.

**Track J: Closing the Pre-Existing CI Debt In Parallel:** While the extraction tracks ran sequentially through the dependency chain, Track J ran independently in parallel to close three CI failures inherited from prior sessions. The migration-chain failure traced to a bridge migration creating a know-your-customer entity with post-rename column names while the subsequent rename migration expected pre-rename names, breaking the sequential state-machine assumption that each migration finds the schema in the exact state the previous migration left it; three columns were corrected to use pre-rename names, and the chain compiled clean. A user-interface package was missing its React type definitions, causing JSX element errors that blocked the type-check job, resolved by adding the type package to development dependencies and correcting an enum cast where a literal const assertion did not match the canonical wallet notification status enum. A second user-interface package required the same React type addition along with a missing optional typing-indicator field on the WebSocket typing payload that two consumer files referenced but the type definition omitted.

**Track I and the Deployment Surface: Turborepo, Dockerfile, and Kubernetes:** The continuous integration track produced the three-stage Dockerfile exposing port 3056, running as a non-root user, and bundling all seven mandatory transitive packages, the Vitest configuration for the new service's test runner, and the lockfile regeneration capturing the new package boundaries. The review-board's production-readiness wave had previously confirmed that Turborepo auto-discovers new applications directories without requiring configuration changes, so no orchestration manifest edits were needed. The Kubernetes deployment manifest mounted the new service into the service mesh routing table at port 3056, completing the path from local compile through container build through cluster deployment.

**Verification Through The Testing Trophy and Documentation Update:** After the extraction landed and was pushed to the remote, the full testing trophy was exercised across unit, integration, and end-to-end layers. The Vitest unit suite ran 378 tests in 4.6 seconds with 369 passes, four pre-existing mock-shape failures identical to those in the host service confirming zero extraction regressions, and five placeholders marked for future implementation. The 100 integration tests across nine files covering team management, API keys, settings, webhooks, settlements, lifecycle, audit log, and validators all passed, exercising the HTTP pipeline through controllers and routes faithfully because the route structure, middleware chain, and dependency injection wiring had been replicated without modification. Two coverage gaps were backfilled with new test files for the query and early-adopter sub-domains. The documentation track updated the project specification to register the extracted service as the 22nd backend service at port 3056, corrected a pre-existing port-number discrepancy in the as-built documentation for the host service, and updated the port-convention reference table.

**Commit Discipline and the F-Series Security Residency Map:** Twenty-two commits landed across the day, organised into nine logical groups mirroring the Clean Architecture layers: scaffold, domain, application, infrastructure, interface, dependency injection, tests, host-service cleanup, three CI fixes, the Dockerfile, Vitest configuration, lockfile regeneration, two documentation updates, and two carry-forward fixes for previously identified decimal-to-number conversions in merchant repositories. The discipline of layer-by-layer commits enables `git bisect` to isolate any future regression to a specific architectural layer rather than to a single monolithic change. A separate by-product of the extraction was the production of an F-series security mitigation residency map, which documented physically where each security control lives across three codebases: invite email binding, audit hash chains, atomic bond locks, and last-administrator removal blocks moved with the extracted service; the constant-time HMAC mitigation, DNS pinning, and per-organization concurrency cap remained in the webhook dispatcher worker; the JWT denylist for scoped tokens stayed in the authentication service. The lesson captured was that security mitigations must be documented with their physical location, not merely their logical purpose, so that when code moves, the residency map confirms whether security travels with it.

Outcome:
The extracted partner service exists as a standalone Clean Architecture service at port 3056 with 172 files comprising 129 source files plus 43 tests, zero non-test compilation errors confirmed by the TypeScript no-emit compiler, and approximately 12,000 lines of code carved cleanly out of a 41,444-line host service. Twenty-two commits landed across eleven parallel tracks with all five priority-zero amendments and all seven priority-one amendments incorporated, three CI failures closed (migration chain, two user-interface type-definition packages), and 477 of 485 tests passing at 98.4 percent with the four remaining failures being pre-existing mock-shape debt identical to the host service rather than extraction regressions.
