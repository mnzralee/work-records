Title: CI/CD Pipeline Hardening: Trivy Unpublished-Release Recovery, Bounded SSH Retry Wrapper & Dependabot Automation

Objective:
To diagnose a regression that had silently turned the production marketing repository's GitHub Actions pipeline red, identify the precise root causes behind two distinct failures (a security-scan installation 404 and a five-second silent SSH deploy rejection), and pivot from a one-line patch to industry-standard fixes that would prevent recurrence. The secondary goal was to introduce automated dependency-management infrastructure so that the manual pin-rot pattern that produced the failure could not return, while keeping each change atomic, well-commented, and verifiable through a live end-to-end pipeline run.

Work Carried Out:

**Branch Synchronisation and the Trigger That Surfaced the Failure:** The day opened with a routine bidirectional synchronisation between the development and ecosystem branches across the parent repository and its eight submodules using a dedicated sync skill. The skill's pre-flight phase tripped on an untracked screenshot reference image that had been placed into the production repository's public-assets directory the previous day, enforcing the strict rule that no synchronisation may proceed against a dirty working tree. The asset was committed deliberately as a tracked reference under a chore-scoped commit message rather than stashed or deleted, on the principle that consciously-placed public-directory files belong in git history rather than stash exile. Divergence assessment was lopsided across the nine repositories, with seven sitting at zero-divergence and only the production repository and the parent repository requiring fast-forward merges in the development-to-ecosystem direction. The synchronisation completed with verification rows all clean, but the trivial screenshot push into the production repository's development branch triggered the CI/CD workflow on every push, and that trigger surfaced a regression that had been silently failing for an unknown number of prior runs.

**Failure Diagnosis Across Two Independent Steps:** Inspection of the GitHub Actions run list confirmed the pattern: the new commit had failed where the previous day's three commits had succeeded, against the same workflow definition, the same branch, and the same secrets unchanged since their last rotation a week earlier. Two steps had flagged red simultaneously, the Security Scan and the Deploy, and the failure shapes were entirely different. Pulling the Deploy job log through the GitHub API revealed an alarming pattern: eighty lines of bash echoed cleanly through directory creation, host-key scanning, and SSH config writing, after which the connection probe `ssh -o ConnectTimeout=30 vps5 'echo ...'` was followed by a five-second silence and then `Process completed with exit code 1`. A five-second silent failure ruled out the configured thirty-second connection timeout entirely, pointing instead to an immediate rejection at the network edge, a transient bastion unreachability from the specific Azure-hosted runner egress IP, a momentary fail2ban lockout, or a packet dropped along the path. The previous day's identically-shaped Deploy had completed in twenty-four seconds, confirming that nothing structural had changed and that the failure was environmental rather than authored.

**The Trivy Unpublished-Release Discovery:** The Security Scan failure exhibited a different fingerprint entirely, exiting at the Trivy installation step rather than the scan step itself, with the install script printing a tag-resolution line and then exiting in 0.4 seconds. Direct API testing against the upstream release endpoint confirmed the suspicion: the binary tarball returned HTTP 404, the API tag endpoint returned 404, and only the human-readable tag page returned 200. The release had been formally unpublished. Walking the published release list confirmed that only three recent versions remained available, with everything from v0.26 through v0.69.1 having been yanked, indicating that the upstream maintainers were aggressively garbage-collecting historical releases to force consumers onto current vulnerability databases. The deeper layer of the failure became apparent on close inspection of the workflow definition: the workflow itself did not pin a specific Trivy version; instead, the version pin lived inside the third-party action at SHA `76071ef`, whose internal default `version` input pointed at the now-yanked release. The action's SHA had been pinned for supply-chain safety, and that pinning had inadvertently inherited a time-bomb default that floated against an external mutable release list.

**Reframing the Patch Toward Industry-Standard Fixes:** The initial instinct was a minimal one-line bump of the Trivy version from the yanked release to the latest published one, which would have purchased perhaps three releases of runway before the same bug returned. The framing was sharpened when the request came back as a call for the standard industry practice rather than a duct-tape patch, which inverted the usual reproducibility-via-pinning instinct that applies to most build dependencies. For a security scanner specifically, the goal is the freshest available vulnerability database on every run, and the command-line surface of mature scanning tools is stable enough that floating to latest costs almost nothing while pinning costs reproducibility against an actively-curated upstream. The architectural rule that emerged was that the action's SHA should remain pinned for supply-chain safety, but the scanner version it installs should explicitly track latest, with automated dependency updates closing the residual loop. For the SSH probe failure, the industry posture is a bounded-retry wrapper around the connectivity probe only, never around the deploy itself, since the deploy contains non-idempotent steps including blue-green port swaps, an Nginx reload, and state-file rotation that must remain single-shot.

**The Three-Commit Atomic Fix:** Three changes were applied as separate atomic commits on the same workflow file pair, each with a focused subject line and a paragraph-length body capturing what had broken, why the fix took its specific shape, and what had been measured. The first commit added an explicit `version: latest` input to the Trivy action step alongside an eight-line comment block documenting the rationale, overriding the action's baked-in default so that future upstream unpublish events could not break the pipeline. The second commit replaced the single-line SSH probe with a twenty-line bash for-loop implementing three attempts with graduated five-second and ten-second backoff intervals, with an inline comment making explicit that the retry wraps only the connectivity probe and never the deploy operation itself. The third commit introduced a new sixty-nine-line `.github/dependabot.yml` configuration file covering three ecosystems (GitHub Actions, npm, and Docker base images) on a weekly schedule, with grouping rules that batch patch and minor npm updates into a single pull request while still routing major-version updates through individual reviews so that breaking-change inspection cannot get hidden inside a batched bump.

**Two Operational Insights Captured for the Memory System:** The diagnosis surfaced two non-obvious operational truths that warranted explicit capture for future work. The first was that pinning a third-party action by commit SHA does not freeze the tools that the action installs at runtime; the supply-chain reasoning that produces the pinning instinct creates a false sense of completeness, because the action's defaults and inputs continue to float against the external world. The action's bytes are frozen, but the binaries it fetches from upstream release pages remain mutable. The second was that the upstream maintainers of the security scanner unpublish historical releases aggressively, a practice not documented in any official channel but empirically observable from the release list, with the corollary that security scanners should be treated as latest-floating tools rather than as pinned dependencies. Both observations were noted as candidates for the memory system rather than left as one-off learning that would need to be re-derived next time.

**End-to-End Pipeline Verification on First Attempt:** All three commits were pushed to the development branch in a single push, triggering a fresh CI/CD run that was watched live. All six pipeline jobs passed on the first attempt: the code-quality gate completed in two minutes and twenty-one seconds with lint advisories unchanged, the build-and-push job pushed an image to the container registry in twenty-six seconds, the Security Scan completed in thirty-eight seconds with a fresh download of the latest published Trivy version, the Deploy job succeeded on attempt one of the new retry loop in seventeen seconds, the smoke test confirmed a homepage 200 response with all security headers present in fourteen seconds, and the Discord notification webhook fired in four seconds. The Security Scan duration of thirty-eight seconds versus the prior thirteen-second cache hit reflected the expected one-time cost of fetching a fresh latest binary, an overhead that would amortise across future runs through the action's existing cache layer. The deploy probe had succeeded instantly, so the new retry machinery did not exercise itself in this run, which was the correct outcome since the retry exists to absorb the stochastic minority of runs rather than to slow down the happy path.

**Parent Repository Pointer Advance and Commit Discipline:** The submodule pointer update was committed in the parent repository as a single chore-scoped commit, with the commit body referencing each of the three child commits by hash and subject so that the parent repository's history remains self-describing and a future reader of the parent log can understand what moved without diving into the submodule. The atomic-commit discipline applied throughout the day was deliberate, since the prose stored in each commit body is the artifact that pays compound interest months later when a similar failure mode appears and a developer is squinting at one-line summaries trying to reconstruct context. Short per-line subjects paired with paragraph-length bodies produced commit history that reads as a maintenance journal rather than as a changelog. The session's net cost was five commits across two repositories (one screenshot asset, three CI hardening commits, and one parent submodule advance), two files modified, ninety-eight lines added against two removed, and three CI/CD runs consumed (the original failure, a confirming rerun that exposed a cache-dependent bifurcation, and the post-fix verification run).

**Calibration on Orchestration Pattern Selection:** A reflection captured at the session close concerned the choice not to dispatch a multi-agent orchestration for this work despite the standing preference for orchestration as the default pattern. The fix surface was tightly scoped to two YAML edits and one new configuration file, all on the same file tree with obvious fix shapes after the fifteen minutes of diagnosis, and dispatch overhead for three agents on a three-file change would have been pure coordination tax with no rigour gain. Inline main-thread execution with the work-recording track running in parallel preserved the same documentation discipline as a multi-agent run while eliminating the orchestration overhead. The calibration was noted explicitly: orchestration as default is correct for module-scale work, while one-file hardening patches are best executed inline with continuous work-recording, and recognising the boundary between the two is a skill worth deliberately practising.

Outcome:
The day delivered three industry-standard fixes to the production CI/CD pipeline (a tracked-latest security scanner, a bounded three-attempt SSH retry wrapper, and a sixty-nine-line Dependabot configuration covering three ecosystems on a weekly cadence), executed across five commits in two repositories with ninety-eight lines added against two removed and a first-attempt green pipeline verification across all six jobs in under five minutes total. The pipeline is now resilient to upstream release unpublish events, absorbs transient network rejection on the SSH probe without weakening deploy atomicity, and self-maintains its action SHAs and dependency versions through automated weekly dependency updates rather than through silent manual pin-rot.
