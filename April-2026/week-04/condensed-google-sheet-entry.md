Thursday, April 23rd, 2026 — CI/CD Pipeline Hardening: Trivy Unpublished-Release Recovery, Bounded SSH Retry Wrapper and Dependabot Automation

Objective: Diagnose a regression that had silently turned the production marketing repository's GitHub Actions pipeline red, identify the precise root causes behind two distinct failures, and pivot from a one-line patch to industry-standard fixes that would prevent recurrence, while introducing automated dependency-management infrastructure so that the manual pin-rot pattern that produced the failure could not return.

Branch Synchronisation and Two Independent CI Failures
The day opened with a bidirectional synchronisation between development and ecosystem branches across the parent repository and its eight submodules using a dedicated sync skill. The skill's pre-flight phase tripped on an untracked screenshot reference image that had been placed into the production repository's public-assets directory, enforcing the strict rule that no synchronisation may proceed against a dirty working tree. The asset was committed deliberately as a tracked reference. The trivial screenshot push triggered the CI/CD workflow which surfaced a regression silently failing for an unknown number of prior runs. Two steps had flagged red simultaneously with entirely different failure shapes. The Deploy job log revealed an alarming pattern: 80 lines of bash echoed cleanly through directory creation, host-key scanning, and SSH config writing, after which the connection probe was followed by a five-second silence and exit code 1. A five-second silent failure ruled out the configured 30-second connection timeout entirely, pointing to immediate rejection at the network edge.

Trivy Unpublished-Release Discovery and Reframing Toward Industry-Standard Fixes
The Security Scan failure exhibited a different fingerprint, exiting at the Trivy installation step rather than the scan step, with the install script printing a tag-resolution line and exiting in 0.4 seconds. Direct API testing against the upstream release endpoint confirmed the binary tarball returned HTTP 404, the API tag endpoint returned 404, and only the human-readable tag page returned 200. The release had been formally unpublished. Walking the published release list confirmed that only three recent versions remained available, with everything from v0.26 through v0.69.1 yanked, indicating aggressive garbage-collection to force consumers onto current vulnerability databases. The deeper layer became apparent on close inspection: the workflow itself did not pin a specific Trivy version; instead, the version pin lived inside the third-party action at SHA 76071ef whose internal default version input pointed at the now-yanked release. The action's SHA had been pinned for supply-chain safety, and that pinning had inadvertently inherited a time-bomb default that floated against an external mutable release list. The initial instinct was a minimal one-line bump which would have purchased perhaps three releases of runway. The framing was sharpened to apply the standard industry practice rather than a duct-tape patch: for a security scanner specifically, the goal is the freshest available vulnerability database on every run, with the architectural rule that the action's SHA should remain pinned for supply-chain safety while the scanner version it installs should explicitly track latest.

Three-Commit Atomic Fix and Two Operational Insights
Three changes were applied as separate atomic commits each with a focused subject line and a paragraph-length body. The first commit added an explicit version: latest input to the Trivy action step alongside an eight-line comment block documenting the rationale, overriding the action's baked-in default so that future upstream unpublish events could not break the pipeline. The second commit replaced the single-line SSH probe with a 20-line bash for-loop implementing three attempts with graduated five-second and ten-second backoff intervals, with an inline comment making explicit that the retry wraps only the connectivity probe and never the deploy operation itself since the deploy contains non-idempotent steps including blue-green port swaps, Nginx reload, and state-file rotation that must remain single-shot. The third commit introduced a new 69-line .github/dependabot.yml configuration covering three ecosystems on a weekly schedule with grouping rules that batch patch and minor npm updates into a single PR while routing major-version updates through individual reviews. The diagnosis surfaced two non-obvious operational truths: pinning a third-party action by commit SHA does not freeze the tools that the action installs at runtime, and security scanners should be treated as latest-floating tools rather than as pinned dependencies because upstream maintainers unpublish historical releases aggressively.

End-to-End Pipeline Verification and Calibration on Orchestration Pattern Selection
All three commits were pushed in a single push triggering a fresh CI/CD run. All six pipeline jobs passed on the first attempt: code-quality gate completed in 2 minutes 21 seconds, build-and-push pushed an image in 26 seconds, Security Scan completed in 38 seconds with a fresh download of the latest Trivy version, Deploy succeeded on attempt one of the new retry loop in 17 seconds, smoke test confirmed homepage 200 with all security headers in 14 seconds, and Discord notification fired in 4 seconds. The submodule pointer was committed in the parent repository as a single chore-scoped commit referencing each child commit by hash and subject.
