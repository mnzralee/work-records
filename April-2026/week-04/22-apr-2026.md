Title: Wireframe-to-Shipped-Code Reconciliation, Recovery-Model UX Decisions & Marketing Site Content Surgery with Source-of-Truth Hierarchy Overhaul

Objective:
To reconcile the wallet wireframe artefact against the shipped registration code by walking the screen catalogue end to end, eliminating screens that documented features the protocol does not actually implement, and producing a clean decision log that can be handed to the design generation pipeline as the source of truth for a branded mobile-first visual pass. The secondary goal was to redesign a homepage participants grid into a four-peer layout, sweep four unrelated infrastructure warnings out of the dev console, rebuild the public-facing individuals page against newly-surfaced authoritative content directories, and restructure the project's source-of-truth hierarchy so future sessions read content authority before consulting any individual specification.

Work Carried Out:

**Wireframe Drift Audit and the Framing Question:** The day opened as a whiteboard session rather than a coding session, prompted by the realisation that the previous evening's wireframe additions for KYC onboarding, post-approval setup, and basic registration had left the consolidated wireframe file in a state where the structural skeleton was correct but the content of several screens had drifted away from the shipped registration flow. Specific screens described a wallet that derived a fabric user identifier from a chosen handle during registration, presented new participants with a 12-word recovery phrase, and offered returning participants a phrase-based restore path. None of these capabilities exist in the shipped codebase or on the roadmap. The framing question for the four-hour walkthrough became explicit: before the wireframe is handed to the design generation pipeline as the canonical source for the branded mobile-first visual pass, which screens describe features that are actually going to be built and which describe features that the wireframe is silently committing the team to. Each ghost-feature screen was treated as a load-bearing piece of spec drift rather than a harmless aspirational sketch, because once a wireframe is rendered into a branded visual it becomes far more expensive to retract.

**Decision One: Removal of the 12-Word Recovery Phrase Throughout:** The first and most consequential decision was the wholesale removal of every 12-word recovery phrase reference across the wireframe. The phrase appeared as a secondary call-to-action labelled "RESTORE EXISTING WALLET 12-WORD PHRASE" on the welcome screen and as an entire dedicated screen displaying twelve BIP39-style words with copy, save-to-keychain, and verification interactions. A walk through the shipped registration wizard confirmed the step machine consists of email, name and country, phone, liveness, and password — five steps with no mnemonic generation, no BIP39 wordlist, no checksum logic, and no restore endpoint anywhere in the codebase. The recovery model is structurally a password-plus-identity model gated on re-verification of email, phone, and where applicable the KYC document set, which is a fundamentally different mental model from the self-custodial seed-phrase model that the wireframe was implying. Drawing a 12-word screen would have signalled to participants the same cognitive frame every other crypto wallet uses, namely that the phrase is the money, must be engraved on metal, and cannot be recovered if lost — an actively wrong message for a public-utility protocol where institutional account recovery is a first-class concern. The alternative of marking the screen as pending was rejected because the pending convention is reserved for screens the team intends to build, and a recovery-kit replacement was rejected because any visible recovery artefact in the UI would re-anchor the participant in the self-custody mental model the protocol design is deliberately moving away from.

**Decision Two: Welcome Screen Reduction to a Single Entry Path:** The recovery-phrase removal cascaded into the welcome screen, which had been carrying two calls-to-action: a primary one beginning genesis registration and a secondary one offering wallet restoration via the phrase. The secondary call-to-action was removed entirely, collapsing the welcome screen to a single-path layout consisting of welcome copy, the load-bearing positioning disclaimer that frames the unit as a non-speculative protocol asset, the primary call-to-action, and a footer indicating that proceeding constitutes acceptance of the protocol specification and privacy notice. The reasoning was that a two-call-to-action welcome screen implicitly tells the participant the population splits into new participants and people-with-a-phrase, which is the wrong taxonomy. The two real populations are new participants and returning participants, and returning participants are served by the dedicated sign-in route rather than by any welcome-screen escape hatch. Collapsing to one call-to-action also produces a visually quieter screen, which aligns with the editorial brand direction set for the design handoff.

**Decision Three: Wholesale Replacement of the Handle Screen:** The longest discussion of the day surrounded the third basic-registration screen, which the wireframe drew as a handle-selection screen complete with availability checking, a five-suggestion chip row, a fabric identifier badge previewing the 20-character structured identifier, and a footer claiming that the fabric user identifier is derived from the chosen handle. Four compounding errors were identified in this screen. There is no handle column on the user profile schema, no handle-uniqueness checking endpoint in the authentication service, and no handle reservation flow anywhere in the registration code. The dotted-suffix convention being suggested would overload an existing domain naming convention and pull the protocol toward a dotcom-era identity framing the team had explicitly rejected. The fabric user identifier is generated by the chaincode genesis-registration algorithm after KYC approval rather than derived from any handle, which means the screen was inverting the identifier's actual provenance. Most concretely, the shipped registration wizard collects first name, last name, and country at this step position, with name validation rejecting strings shorter than two characters, country selection from a structured list, and a preflight request that surfaces a warning when the country's genesis allocation is in a pending state. The screen was therefore replaced wholesale, renamed from a handle screen to a details screen, and rewired to collect first name, last name, and country with no fabric identifier preview, no availability check, and no suggestion row. Handles as a feature were debated for nearly an hour as a possible post-KYC optional layer mapping the participant identifier to a friendlier label, but were ultimately deferred to a much later module band on the basis that they require an on-chain uniqueness registry, impersonation-protection logic, and a re-introduction of the dotted-suffix temptation, none of which justify the scope cost given that the existing 20-character structured identifier is already legibly human-copyable.

**Decision Four: Password Strictness Disclosure on the Final Registration Step:** The fourth decision concerned the password screen, where the existing copy correctly described the password's daily use but said nothing about the consequence of losing it. Because the recovery model is structurally non-mnemonic, the password is materially more important than it is in a self-custodial wallet where the phrase is the ground-truth authority, and a participant choosing a weak password without understanding the recovery story is being set up for a slow and non-trivial re-verification path. A second explanatory block was added directly above the password input stating that recovery is strict by protocol design, that losing the password requires re-verifying email, phone, and identity documents for KYC-approved wallets, that there is no recovery phrase and no shortcut reset path, and that the participant should store the password in a password manager or another safe location. The block was deliberately placed inline with typographic weight rather than presented as a modal, a checkbox-gated acknowledgement, or a separate screen, on the reasoning that checkboxes train participants to tick without reading and that an extra screen in a multi-step wizard adds a drop-off point that pushes the sign-up task further away. The framing positions strict recovery as a protocol property rather than a limitation, because for a public-utility financial protocol soft recovery is structurally a security hole rather than a convenience.

**Sub-Decisions, Step-Count Reconciliation, and Carry-Forward:** Two sub-decisions were captured for follow-up rather than executed in the same session. The first was whether the date-of-birth field should be moved from the KYC personal-information step into the basic-registration details screen, a change that would push a currently KYC-scoped data point into pre-KYC retention scope and therefore carries compliance implications that should not be decided on a whiteboard; the default carry-forward is to keep date-of-birth in KYC and to leave visual room on the details screen in case compliance review later approves the move. The second was a step-count reconciliation: the wireframe had been drawing a seven-step wizard while the shipped wizard is five steps, with the seven counting a standalone welcome screen, an inline OTP step that the shipped flow draws as a sub-step of email rather than its own screen, and the now-removed handle screen. The wireframe will be rewired to a five-step total in a subsequent edit pass after final step numbering is agreed, but the file change itself was deliberately not made today because step renumbering belongs in its own commit rather than being mixed in with content corrections. A pre-existing structural reorder in the same file, which had moved the basic-registration and KYC sections ahead of the core navigation, transfer, and receive sections to match the actual participant journey, was left in place because the new order matches the narrative sequence a new participant follows.

**Design Handoff Brief Architecture:** The reason the four decisions matter operationally is that the next session's first task is to hand the consolidated wireframe to the design generation pipeline to produce a branded, mobile-first, visually-polished pass of the entire wallet. The wireframe in its current form is deliberately monochrome, fixed-width typed, and structurally austere, and the design pipeline is going to take it and return visual inspiration matching the protocol's brand voice — public-utility credibility, editorial calm, and explicit rejection of crypto-launch aesthetics. The brief itself was scaffolded into three parts during the session: a render list specifying the seven basic-registration screens, the seven KYC screens including the resubmit loop, the five core-navigation screens including the registered-but-unapproved limited dashboard, the eight transfer screens, the four receive-request-scan screens, and four standalone screens for PIN, biometric, guardians, and the post-approval done state, with an explicit exclusion list naming the recovery phrase screen, the welcome screen's secondary call-to-action, and the handle screen as artefacts that must not appear in the visual pass; a brand-voice section calling for mobile-first, editorial rather than commercial framing, central-bank-annual-report density, typographic hierarchy over colour, and the load-bearing disclaimer copy held visible and prominent; and a what-we-are-not-asking-for section explicitly excluding glassmorphism, dark-mode-first variants, and stock abstractions of coins or chains.

**Homepage Participants Grid Rewrite and Responsive Padding Calibration:** The afternoon shifted from wireframes onto the marketing site, beginning with the conversion of the homepage's "Built for Every Participant" section from a three-card glass-morphism layout to a four-card full-bleed grid that adds non-profit organisations as a distinct peer rather than a sub-type of business. The visual change was simultaneously a factual correction because non-profits are a separate trust tier at the identity level with distinct endorsement rules, fee treatment, and grant access. Three design tradeoffs were resolved before code was written: full-width hairlines on top and bottom were chosen over partial 60% borders because the latter typically reads as a rendering bug rather than an intentional flourish; a uniform light purple wash at roughly five and a half percent opacity was applied to all four cells rather than mixing purple and green, because mixing colours implicitly signals one cell is preferred and contradicts the equal-peer header copy; and per-cell content was kept minimal with a numbered index, a heading, a one-line description, and a hover-revealed arrow, allowing the additional whitespace from the larger cells at full-bleed width to do the editorial work. Implementation produced a new component with four link cells and an explicit border architecture in which left-column cells carry a right border, top-row cells carry a bottom border, and the last mobile cell suppresses its bottom border. The first preview surfaced a responsive-padding miscalibration on wide monitors: at 1920 pixels each cell is roughly 960 pixels wide, and the initial 56-pixel side padding left content hugging the viewport wall. The fix was a five-step breakpoint ramp scaling per-cell padding from 24 pixels on mobile through 48, 80, and 112 pixels at intermediate breakpoints to 160 pixels on the widest viewport, while the grid container itself remained full-bleed so the hairlines continue to touch the wall at every breakpoint and only the inner content pulls inward. An asymmetric top-only spacing class was also substituted for the standard symmetric section spacing immediately below the grid, because the bottom hairline already serves as the visual terminator and a symmetric bottom pad was producing an empty band before the next section.

**Infrastructure Warning Sweep Across Four Distinct Dev-Console Issues:** Once the grid landed, a dev-server preview surfaced four unrelated console warnings that warranted a focused twenty-minute sweep before continuing design work. The first was a content-security-policy violation in which the dev bundler's call-stack reconstruction feature relied on dynamic evaluation that the production-grade script-source directive was correctly blocking; the resolution was to add the dynamic-evaluation source conditionally on the runtime environment so that production stayed locked down while the dev environment unblocked the bundler, with WebSocket sources also added to the connection-source directive for hot-module-replacement traffic. The second was a cluster of edge-runtime warnings tracing through the instrumentation hook into a campaign worker that imports Node-only crypto and process modules; the existing runtime guard checking for the presence of the Node process object worked at execution time but did not communicate any information to the bundler's static import tracer, so the tracer continued to follow the imports into the edge bundle graph and warned about them even though they would never execute. The fix was to gate on the bundler-defined runtime constant, which is compile-time per bundle, so the edge build now sees a dead branch and discards the entire downstream import graph. The third was a logo aspect-ratio warning where both width and height were being driven to auto without an established intrinsic ratio; the technically-correct fix per the framework documentation rendered the logo at literally 32 pixels because the previous incorrect-but-coincidentally-working combination had been interacting with navigation padding classes to produce a larger rendered size, and the change was reverted on user callout because the dev-only console noise is cheaper than a regressed logo size. The fourth was an image-quality declaration warning that required adding the non-default quality value to the explicit qualities array. The instrumentation fix was the most strategically valuable of the four because it generalises to every future worker-style integration that imports Node-only modules into the same application.

**Pre-Registration Call-to-Action Band on Research Section:** A pre-registration call-to-action was added to the research section of the homepage. Rather than dropping in an identical primary button matching the hero call-to-action, which would have read as a scroll-back-up repeat and either implied the two were the same link or generated a feeling of being nagged, the same primitive button component was wrapped in a contextual band giving it a distinct reason to exist at this position in the page. The band sits below the two research cards as a full-width card with a subtle gradient wash at low opacity, an overlaid grid pattern at twelve-percent opacity matching the dark section's existing background motif, and an editorial eyebrow-headline-subtitle on the left with the primary button on the right. The gradient wash positions the band as an action element visually distinct from the research cards above without competing with them as content, the subtitle copy clarifies the offer in a different voice from the hero, and the button carries a distinct analytics attribute so clicks from this position are segmentable from hero clicks downstream.

**Individuals Page Rebuild with Atmospheric Hero, Stats Banner, and Live Verification:** A research agent was dispatched to audit the existing individuals page against the protocol specification before any redesign was attempted, and four significant findings came back. A claimed phase-two participant cap was a fabrication that did not match any phase boundary in the actual phase distribution; every currency reference used a suffix format where the brand language specification mandates a prefix format that aligns with central-bank conventions rather than crypto-token-ticker conventions; the page contained no mention of the protocol's defining monetary property, namely the velocity mechanism that applies a small annual rate only to idle balances above a threshold held more than a cumulative window; and the page omitted the final phase entirely along with the participant-cap cutoff rule. Three layout options were considered and a hybrid was chosen consisting of an atmospheric hero image at low opacity for warmth, an editorial body of numbered clauses for spec credibility, a single dark pull-out for immutable parameters, and a light closing call-to-action. A first hero image generated through a generative-image service used a network-of-glowing-nodes metaphor that read as crypto-conference imagery and was rejected; the regenerated prompt drew explicitly from documentary photo-essay aesthetics, specifying a single human figure in soft silhouette seen from behind to avoid face-generation artefacts, warm late-afternoon natural light, distant figures going about productive daily life, environment-derived colour grading rather than a forced overlay, and generous negative space for text overlay. The second generation produced a silhouetted figure walking down a sunlit market street in golden-hour light and was accepted at twenty-two-percent opacity behind the hero typography. A new stat-counter component was extracted into the shared user-interface directory rather than the home-section directory so that other sub-pages can adopt the same treatment, replacing the dark-band styling that had pattern-matched to the homepage convention rather than the sub-page convention. A live-testing pass through a browser automation tool captured more than twenty screenshots across desktop and mobile viewports and exercised the page's interactive elements, surfacing two content-security-policy violations from redundant font imports in the global stylesheet that were being silently shadowed by self-hosted variants in the layout. Removing the redundant imports closed all violations and a hero scroll indicator was also stripped on the basis that scroll indicators are a top-level homepage convention rather than a sub-page convention.

**Source-of-Truth Hierarchy Restructure in Project Memory:** The most architectural moment of the session came when two new authoritative content directories were nominated to supersede the older specification directory the previous research had been built against, and a second research agent was dispatched to map the new directories and extract authoritative answers to the specific factual questions the page had been built against. Six confirmed supersessions returned, each changing a number on the page: the total participant target had been revised downward, the country count had been corrected, the phase distribution had been sub-tranched into a finer eight-phase schema with a higher allocation for the earliest cohort, the final-phase allocation value had been raised, the velocity rate band was confirmed against new audit documentation, and a government-treasury split was established that would feed into a separate sub-page rebuild. A new content language guideline was identified as superseding the older language specification, with a stricter prohibited-phrases list and explicit replacement guidance. The page constants were updated to reflect the new schema and the corrected country count. More consequentially, the project's root memory file was restructured with a new content-source-of-truth hierarchy section placed before the existing module documentation table, defining a three-tier authority scheme in which one tier holds the authoritative numbers and voice, a second tier serves as the explicit conflict-resolver between legacy code and new specifications, and a third tier marks the older specifications as engineering reference only. Inline warnings were added next to the affected module rows in the table and the six supersessions were enumerated by name so that any future session reading the memory file before starting content work sees the authority hierarchy before consulting any individual specification.

Outcome:
The wireframe walkthrough closed with four primary content decisions and two carry-forward sub-decisions documented as a clean decision log ready to ship to the design generation pipeline, with zero commits made on the day because the decisions deliberately precede the next session's mechanical edit pass. The afternoon delivered a four-cell full-bleed homepage participants grid with a five-step responsive padding ramp, three new shared components, three closed content-security-policy violations, four resolved dev-console warnings tracing back to one strategically valuable instrumentation fix, an individuals page rebuilt against six newly-authoritative numeric corrections with a regenerated documentary hero, and a three-tier source-of-truth hierarchy added to the project's root memory file with explicit warnings on three superseded specification rows.
