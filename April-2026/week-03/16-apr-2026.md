Title: Enterprise CI/CD Pipeline Redesign: From Broken Apache Deploy to Production-Grade GHCR Blue-Green Automation

Objective:
To diagnose and resolve a chronically failing GitHub Actions deployment workflow, pivot from a patchwork fix to a full architectural redesign of the production pipeline, and drive the new system through specification, multi-agent review, parallel implementation, and live pipeline validation. The secondary goal was to execute a systematic data integrity refresh across two interactive analysis pages after discovering that shared-branch divergence had rendered every published figure stale, and to complete a site-wide visual consistency pass standardising dark section treatments across the marketing site.

Work Carried Out:

**Branch Synchronisation and Operational Debt Discovery:** The session opened with what was expected to be a routine branch sync across the parent repository and eight submodules, merging the development and ecosystem branches. The sync surfaced three sources of operational debt that warranted explicit correction. One submodule had been left on another developer's feature branch, sitting two commits ahead with partner-page work but twenty-eight commits behind the mainline; these had to be reconciled through a merge that added five new page files and 914 lines. A one-directional merge mistake was also exposed: the ecosystem branch carried twenty-nine commits of marketing, dashboard, and research updates that had never flowed back into the development branch, leading to a marketing dashboard file existing on one side but not the other. A whitepaper version discrepancy was discovered where the MDX file still showed version 7.03 despite six peripheral marketing documents referencing version 8.0. These painful manual reconciliations motivated the creation of a 265-line bidirectional sync skill codifying a strict six-phase procedure (pre-flight, fetch, assess, sync submodules bottom-up, sync parent, verify) with explicit conflict-resolution guidance and known edge cases.

**CI/CD Failure Diagnosis and Architectural Pivot:** The GitHub Actions blue-green deployment workflow had been silently failing on every run. Inspection of the log traced the failure to a `sed` command attempting to modify `/etc/httpd/conf.d/gxcoin.money.conf`, a file that does not exist on the production server because the server runs Nginx rather than Apache. The build phase (eighty-nine seconds, seventy static pages) and the Docker container health check (passing on all thirty retries) both succeeded, but the traffic-switch step was attempting to modify a non-existent Apache configuration on every deployment. A quick substitution of Nginx equivalents was drafted, but an honest assessment of whether the pipeline met enterprise standards revealed eight deeper design problems: Docker builds consuming production server CPU and RAM, full git clones placing source code on production, environment files with API keys stored in plaintext on disk, CI and CD being completely disconnected, no container registry, no public-URL smoke tests, no deployment notifications, and no vulnerability scanning. The decision was made to pause the patch and conduct comprehensive research before rebuilding.

**Deep Industry Research and Registry Selection:** A research agent was dispatched to conduct comprehensive industry analysis across ten areas, including enterprise CI/CD architecture patterns, container registry comparison, blue-green deployment patterns on single servers, Next.js standalone Docker deployment, GitHub Actions best practices for 2025-2026, Trivy image scanning, environment protection rules, SSH deployment security, Discord notifications, and Nginx reload atomicity. The resulting 2,500-word sourced report established several architectural foundations: GitHub Container Registry was selected because it requires no additional credentials and carries no rate limits; production servers must only pull pre-built, pre-scanned images to eliminate build-time resource consumption; every container must be tagged with its exact commit SHA for traceability; and registry-based Docker layer caching with `mode=max` was chosen over the 10GB-limited GitHub Actions cache. A critical supply-chain finding from March 2026 established that seventy-six of seventy-seven release tags of a popular scanning action had been compromised by credential-stealing malware, making SHA-pinning of all third-party actions a non-negotiable P0 requirement rather than a best practice.

**Production Server Audit and Environment Reality Check:** An SSH-based audit of the production server was conducted to ground the design in actual infrastructure rather than assumptions. The server ran AlmaLinux 10.1 using `/etc/nginx/conf.d/` rather than the Debian-style `sites-available/` pattern, meaning even the initial quick-fix sed path would have been wrong. Nginx 1.26.3 was configured with a production-hardened two-hundred-line configuration featuring Cloudflare real-IP restoration, twenty-eight bot-blocking patterns, enforced Content Security Policy, rate limiting of thirty requests per second general and ten per second API, WebSocket upgrade support, and static asset caching. Docker 29.2.1 was active with a green container serving port 3003 and a blue container stopped on port 3000, while 26.7 GB of Docker build cache (19.3 GB reclaimable) had accumulated as a byproduct of building on production. An unexpected discovery was a running K3s cluster consuming memory without any documented purpose. The firewall restricted HTTP/HTTPS to Cloudflare IPs only, Let's Encrypt certificates were valid through May 2026, and a 743-line manual deploy script already existed which correctly handled blue-green switching with Nginx.

**Specification Authoring and Nine-Agent Review Board:** A 703-line specification was authored covering thirteen architectural decisions with rationale and alternatives, six pipeline stages (Quality Gates, Build and Push, Scan, Deploy, Smoke, Notify), four implementation phases, the full server audit embedded as reference, deployment script design, Nginx traffic-switching pattern, rollback strategy, security hardening measures, fourteen acceptance criteria, and eleven verification test cases. A nine-agent three-wave review board was then convened. Wave one dispatched an infrastructure auditor that SSH-verified over sixty individual spec claims against the live server, a CI/CD industry researcher that cross-referenced twenty external sources, and a codebase analyst that identified four critical issues including a Node version mismatch (CI on 20, Docker on 22), missing Dockerfile ARG entries, and eleven undocumented runtime environment variables. Wave two dispatched a security reviewer that produced eighteen findings including two critical vulnerabilities, a GitHub Actions expert that produced a complete 300-line workflow YAML, a deploy script specialist that produced a 350-line shell script, and an environment variable specialist that produced a complete 22-variable audit. Wave three synthesised all findings into a thirty-eight-item registry identifying six pre-execution blockers. Final metrics were two critical findings, sixteen high, fifteen medium, and five low.

**Critical Vulnerability Surfaces and Blocker Remediation:** The review board surfaced two vulnerabilities that predated the pipeline work but had escaped prior attention. The first was that a maintenance-bypass password exposed as a `NEXT_PUBLIC_` build-time variable was being inlined into every JavaScript bundle served to every visitor, extractable with a simple DevTools search, and compounded by a hardcoded fallback string in source. The fix was to remove the variable from the build pipeline entirely and defer a proper server-side middleware implementation as a separate code change. The second was a sudoers rule proposing `sed -i *` which effectively granted arbitrary file-modification rights; this was replaced with a locked-down wrapper script at `/usr/local/bin/gxcoin-switch-upstream.sh` that accepts exactly two port values (3000 or 3003) and performs a block-scoped sed restricted to the upstream directive only. SSH key scoping was re-architected into separate ED25519 key pairs for bastion and target hosts to shrink the blast radius of any single leaked key. The environment variable audit was converted from a loose list into a precise table of four build-time variables and fourteen runtime variables, identifying two dead or misclassified entries along the way. Six blocker amendments were applied in a single editing pass, growing the specification from 703 to 928 lines with forty-four explicit review-board back-references.

**Parallel Multi-Agent Pipeline Implementation:** With the specification approved, two implementation tracks were launched in parallel. The server-preparation track completed ten steps including creation of a restricted `deploy` user, directory structure at `/opt/gxcoin/`, the Nginx wrapper script, sudoers rules, migration of the runtime environment file (forty-eight variables, chmod 600), and generation of a dedicated ED25519 SSH key pair. A runtime discovery during this track showed that `systemctl reload nginx` fails when called from a subprocess on AlmaLinux due to `PrivateTmp=yes` in the nginx systemd unit; the wrapper was adjusted to use `nginx -s reload` to send SIGHUP directly to the master process. The code-implementation track produced the updated Dockerfile with the critical maintenance-password removal, a 472-line unified CI/CD workflow with seven jobs and ten SHA-pinned actions, a 352-line deploy script with `flock` mutual exclusion and seven exit codes, an environment example file documenting every variable, and deletion of the 419-line broken Apache workflow. Orchestrator verification confirmed that the Dockerfile had the maintenance password removed (an initial miss caught and corrected during verification), that all actions were SHA-pinned via GitHub API lookup, and that the deploy script used environment variables rather than command-line arguments for credentials.

**The Eighteen-Run Battle to Green:** With the manual GitHub environment and secret configuration completed, the first pipeline triggered and failed at the lint step with a setState-inside-useEffect error and a missing dependency array entry, both inherited from earlier unchecked feature work. This was the precise behaviour the pipeline was designed to enforce. Eighteen total runs were required to reach a fully green pipeline. Runs one and two exercised the code-quality gate; runs three and four exposed that a sub-agent had fabricated commit SHAs for two actions, requiring every remaining SHA to be verified against the GitHub API (a direct validation of the review board's insistence on SHA-pinning at implementation time). Runs five and six encountered paid-plan features (artifact attestation, SARIF upload) that required `continue-on-error: true` for graceful degradation on private repos. Run seven began the SSH authentication saga when the target-host secret was found missing. Runs eight through ten failed because a third-party SSH action's internal proxy implementation was incompatible with the bastion configuration regardless of key layout. Run eleven replaced the third-party action entirely with native OpenSSH and `ProxyJump`, eliminating a supply-chain dependency. Runs twelve and thirteen corrected a YAML heredoc indentation trap that had been silently corrupting the whitespace-sensitive SSH configuration, and fixed a metadata output reading the Docker version tag instead of the commit SHA. Run fourteen revealed that root login was disabled on the bastion through hardening configuration, requiring the bastion user to be switched to an unprivileged account. Run fifteen required adding sudo to the nginx pre-flight check and correcting a sudoers rule that referenced the wrong binary path (`/usr/bin/nginx` versus the actual `/usr/sbin/nginx`). Runs sixteen and seventeen uncovered that Docker build-push with attestation wraps images in a multi-architecture manifest list which cannot be pulled by digest on single-architecture hosts, and that `GITHUB_TOKEN` is scoped to runner environments and cannot authenticate against private GHCR from external hosts. The resolution was to pull by SHA tag rather than digest and to issue a Personal Access Token with `read:packages` scope. Run eighteen executed the full pipeline green end to end: quality gates, build and push to the registry, advisory Trivy scan, deploy to production via OpenSSH ProxyJump in twenty-two seconds, smoke test through Cloudflare returning HTTP 200 in 0.275 seconds with all security headers verified, and Discord notification delivered with commit SHA embedded.

**Data Integrity Refresh Across Interactive Analysis Pages:** A separate workstream addressed data drift between shared development and ecosystem branches. A four-agent parallel audit compared live page data against source dashboards and surfaced systematic drift: one analysis page was missing a country entry (a 201-country source against a 200-country site), and the other was thirty-five percent stale because source recalculation had shifted a key grant constant from 136 to 210, invalidating every allocation figure, grant multiple, and tier placement in 204 typed entries. Two additional country sections had been added to the companion article but were absent from the site. A four-agent parallel extraction reconstructed both datasets programmatically via Node.js evaluation of the source dashboard HTML and mapped every country through the strict TypeScript interface, producing a 201-entry and a 205-entry dataset respectively. Two further parallel agents cascaded updates across seventeen components including statistics cards, detail modals, hero subtitles, table descriptions, page metadata, and homepage counters, while a final sweep caught two stale references that the agents had missed. TypeScript compilation and full production build both passed clean.

**Site-Wide Visual Consistency Pass:** A final visual consistency pass addressed several patterns that had accumulated. The `SectionHeading` component was updated to automatically switch between the standard purple-to-green gradient and a white-to-green dark-mode gradient depending on a theme prop, fixing invisible highlighted words on dark backgrounds site-wide with a single one-line change. A compact homepage bridge section was introduced between two existing sections, using glass link cards with green left-border accents to provide entry points from the homepage into the two heavy analysis pages without repeating their content weight. A standardised dark-section background treatment combining an animated background canvas, layered radial gradients (purple at fifty-five percent on the left and green at eighteen percent in screen-blend mode), grid lines at eight percent opacity, and noise texture at thirty percent opacity was applied uniformly across thirteen dark sections spanning ten pages plus specific components. Three unused icon component files and an empty icons directory were removed after grep verification confirmed zero remaining imports, and the sitemap was updated with two new analysis-page routes carrying weekly change frequency and 0.8 priority.

Outcome:
The day delivered the first fully automated production deployment of the marketing site through a 928-line reviewed specification, a 472-line unified CI/CD workflow, a 352-line deploy script, and a hardened production server configuration, with the eighteenth pipeline run executing green end-to-end in roughly twenty-two seconds and verified through Cloudflare with all security headers present. In parallel, 406 country data entries were programmatically refreshed across two analysis pages, thirty-eight review-board findings were resolved including two critical security vulnerabilities, and thirteen dark sections across ten pages were standardised into a consistent visual treatment, closing the day at roughly 141 commits across the parent repository and submodules.
